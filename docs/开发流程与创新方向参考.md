# ProductGrapher 开发流程、创新方向与评测参考

适用于从 Python 仓库恢复业务架构的开发与评测。项目基线为 **v0.3.0**，源码提交为 `aecd78a`。资料与公开数据核对至 **2026-11-23**。评测对象是**工作台对现有代码的解释是否忠实、完整、可查**。业务需求是否合理、被分析项目应当怎样实现，由项目维护者判断。[基线源码][baseline] · [现有视图和下钻方式][views]

一次最小对照可以这样安排。用 **PyCG** 查调用箭头，用 **SemArc 的 Scrapy 标注**查分组，用 **RepoProbe 的 Python 题**查业务讲解，再让读者从一条带例外的结论找到源码。四项结果分别报告。[开发流程](#workflow) · [创新方向](#directions) · [第三方评测集](#datasets) · [评分办法](#protocol) · [逐项文献与框架笔记](#sources)

## 一、一个版本怎样从问题走到验收

| 阶段 | 具体操作与产物 | 怎样判断可以进入下一步 |
|---|---|---|
| 1. 写下读者要回答的问题 | 选一条真实业务路径，写出“哪个模块负责”“从哪条入口触发”“哪些输入会跳过或拒绝”。在看候选输出前，按固定提交独立记录答案、可接受的替代表述和证据行。 | 第二位读者能从源码重建答案。分组存在多种合理解释时保留备选归属。[可视化任务设计][munzner] · [RepoProbe][rp-paper] |
| 2. 固定输入，建立对照 | 记录仓库提交、实际索引文件、Python 与工具版本、各阶段模型供应商和模型名、提示版本、预算及已保存的模型回复。保留目录分组、当前发布版和拟改版本的结果。 | 相同工具环境和文件可以重放静态图。复用同一份讲解的导出与重新调用模型的运行有不同标识。[项目复现约定][repeat] |
| 3. 先验收代码事实 | 分开生产源码、测试夹具和示例。导出入口绑定、已解析调用、调用位置、已识别条件和未解析记录。在第三方 Python 调用图上逐边核对。 | 每个已展示为静态调用的箭头能还原到调用点。分别记录错连、漏连、未解析和扫描范围，保留失败样本。[本项目协作图实现][collab] · [PyCG 原始评测工件][py-art] |
| 4. 生成业务分组和讲解 | 用已定位的生产入口、实现职责、读写状态和相邻调用提供模型上下文。文档中的业务词可帮助命名。单列实现者、调用者和共享支持者。 | 抽查“为什么归在一起”和“这条关系怎样发生”两类问题。每条讲解指向支持其措辞的代码，语义相似仅参与分组。[SemArc][sem-paper] · [ASNER §3][asner] |
| 5. 用真实读图任务做盲测 | 给读者同一类任务，让其从总览下钻至业务模块、调用点、条件和源码。记录答案、定位时间、误读处。交替呈现不同版本，掩去工具名。 | 同时报告答对率和答对时的定位耗时。读者找错分支时记录停在哪一层，即使全部链接都能打开。[ArchAgent §4.1][aa-paper] · [可视化评估][munzner] |
| 6. 决定是否保留改动 | 每轮先改变一个因素，例如只增加调用前的退出条件。相同输入做配对比较，保留所有首次输出、错误和重试。 | 目标指标有可解释的改善，其他关键指标与成本一同列出。改善只出现在熟悉的示例时，保留为假设，换留出仓库复核。[RepoProbe 评测与数据][rp-data] |

## 二、值得用实验检验的创新方向

静态分析加 LLM、多层架构图、源码跳转和仓库问答都有直接先例。当前版本的基础是三种视图共用源码快照、协作箭头保留调用点和部分路径条件、总览结论保留引用。以下按优先级列的是**待验证的项目假设**。每项都给出了足以推翻它的对照。[当前工作台][views] · [开源产品对照][cb] · [已有证据机制][lens]

| 优先级与假设 | 在现有工作台上怎样改进 | 有什么结果才值得继续 |
|---|---|---|
| **P1　同一条业务关系能讲清不同入口的触发条件和例外** | 从每个调用点分别保留入口、前置检查、动作和证据，再汇总到同一条模块箭头。区分“决定是否调用”和“改变输出值”。无法解析的动态目标保留未知。先在现有协作图和总览复核上做小范围对照。 | 相对 v0.3.0，留出仓库中漏掉、说反或套到错误入口的条件减少，凭空出现的调用也单独计数。对照只给最近一个 `if` 和给完整相关证据两种输入。[业务条件提取][hatano] · [Python 控制流][codeql] · [现有总览事实提取][facts] |
| **P2　用职责证据区分近义模块和共享支持者** | 提议合并时同时展示共同实现的业务职责、各自拥有的状态和反例，例如甲只调用乙、甲只在测试中使用乙。允许保留独立或共享归属，允许读者看到判断依据。 | 对照目录分组、现行分组、加职责证据的分组。除文件配对得分，还检查“共享组件被吞并”和“同一职责被切碎”各有多少。关掉职责证据后仍同样好，便没有采用它的依据。[现有分组合并][groups] · [SemArc 标注][sem-labels] · [ASNER][asner] |
| **P3　验证模型的一句话，同时检查源码依据和关键遗漏** | 把含多个事实的结论拆为可核对的断言，各自连接到同一快照的证据片段。多个调用点各有一条证据路径。新提交到来时区分引用位置变化和实际条件变化，再复查受影响的断言。 | 分别用仅移动行号、改变判断条件、删除一个调用点的版本做配对测试。统计过时结论被识别的比例、仍成立却被误报的比例，以及人类定位耗时。[ALCE §3.3][alce-full] · [数据库溯源][prov] · [Arch Lens][lens] |

**用订单例子校准判定。** `return_goods` 先校验订单，再拒绝无对应分配、尚未发货或超量的退货。对通过检查的请求，可售品增加可用库存并调用 `retry()`。其他值走损坏分支，更新损坏库存并跳过该调用。“退货后会重试”即使正好引用调用行，也会误导读者。给这条结论打分要分别看前置拒绝、可售分支、另一分支，以及引用是否覆盖各自的实现。这个例子适合调试评分规则，第三方成绩应使用独立样本。[退货处理源码，第 160–187 行][return-case]

## 四、实验记录和计分办法

按仓库划分调参集与留出集。索引输入只包含待分析的源码仓库，人工参考图、评分清单和答案存放在索引目录之外。每次比较保留待测版本、输入提交、实际索引文件清单、排除原因、供应商与模型标识、每阶段调用次数、耗时及可获得的 token 用量。记录首次输出，再另外记录重试，包含空图、失败、部分生成和无法解析的样本。比较处理方法时固定模型与预算。比较本地、云端模型时，每次只替换一个阶段的模型，复用其他阶段的产物。精确复现模型措辞时使用已保存的讲解和源码快照。[当前快照设计][repeat] · [RepoProbe 评测设置][rp-paper]

| 问题 | 比较对象和计算办法 | 怎样读这个分数 |
|---|---|---|
| 调用边画得准吗 | 固定节点命名和范围后，令 $h$ 为命中边数，$p$ 为预测边数，$g$ 为参考边数。精确率 $P=h/p$，召回率 $R=h/g$，$F_1=2h/(p+g)$。逐仓报告原始计数再取宏平均。 | 分开报告“调用”和“入口绑定”。空分母记为不适用，同时给计数。函数对命中只验证目标身份，行号与条件要另外核对。[PyCG][py-paper] · [ArchAgent §4.1][aa-paper] |
| 业务模块分得清吗 | 将预测中的符号按成员文件投影，显式保留跨组文件。**本项目建议**将两个不同文件至少共属一个组计为正例，比较预测与人工参考的同组文件对，算精确率和召回率。另报覆盖的参考文件数、遗漏文件和最大的误合并。 | 对单一归属且文件全集对齐的部分可补充调整兰德指数（ARI），并列出这部分占全集的比例。人工架构标签检验职责边界，业务命名仍需人读。小仓和大仓分别给数。[SemArc 原始标签][scrapy-gold] · [ASNER §4.1][asner] |
| 讲解既有依据又完整吗 | **本项目建议**分别计算“证据充分的输出断言数 / 全部可核查输出断言数”与“讲解正确交代的必需条件和例外数 / 事前标注的必需项数”。逐项记录支持、矛盾、材料不足、遗漏。另查引用是否能定位到该提交的文件行。 | 第一个比例约束凭空增加的结论，第二个比例揭示保守省略。把条件安到错误入口不能算命中。整段源码能打开仅算定位成功。[ALCE §3.3][alce-full] · [RepoProbe §4][rp-paper] |
| 圈选问答与阅读真的有帮助吗 | 开放题用 RepoProbe 原始分项计分，选择题用 SWE-QA 选对率。另设人工任务“找出什么输入会跳过某动作，给出源码证据”。记录答对人数/总人数、正确任务的中位耗时和走错的分支。 | 比较 v0.3.0、改动版、同一模型直接读仓库。图上导航另与 CodeBoarding 对照。对不同工具提供相同仓库和提问机会，无法运行的对照列为缺测。预先交替工具与等价任务顺序，减少第二次看同题的学习效应。[RepoProbe][rp-paper] · [SWE-QA][swe-paper] · [Munzner][munzner] |

**可直接照做的首轮顺序**

1. 锁定 PyCG 原始微型集，先用 `assignments/chained` 核实符号名和期望边的对齐方式，再跑全套 112 例。遇到未支持语法仍记入全量结果。[样例输入和期望边][py-case]
2. 在 Scrapy 固定源码上对齐参考路径，例如 `core/engine.py` 对应包源码目录内的文件。先报告对齐率，再比较目录分组、v0.3.0 和候选分组，保留 `utils/engine.py` 的两个标签。[原始标签][scrapy-gold] · [参考快照][asner]
3. 用 RepoProbe 的干净快照校准输入格式，再跑预先选定的 34 道 Python 架构与业务题。向模型仅提供仓库、图和题干。需要外部服务资料或非 Python 源码才能回答的题保留原编号，单列覆盖范围。人工复核所有来源不足或条件矛盾的候选断言。[题库][rp-data] · [版本清单][rp-meta]
4. 在留出的真实仓库上做一次条件与例外盲测。预先标好哪些事实必须讲出，把漏掉条件的流畅答案与指出分析边界的答案分开记录。汇报每仓结果、首次失败、成本以及读者复核时间后，再决定是否扩大样本。[核对方法][alce-full] · [读者任务设计][munzner]

准备好 Python 环境后，可先在 ProductGrapher 根目录运行现有回归测试，再用工作台自身的源码验证导出入口。在 PowerShell 中执行以下命令，HTML 和可供比对的 JSON 会写入临时目录。做外部评测时，把命令中的源码目录 `./how2trust` 换成已固定版本的待测源码目录。

```powershell
python -m unittest discover -s tests -v
python -m how2trust export ./how2trust -o "$env:TEMP/productgrapher-self.html" --json "$env:TEMP/productgrapher-self.json"
```

每次实验最终保留一行摘要，字段为 **仓库/提交、工具配置、覆盖范围、调用边精确率/召回率、分组得分、断言证据充分率、条件与例外覆盖率、读者答对率/耗时、失败数/成本、可回放产物**。首轮已记录 Scrapy 的调用点抽查、订单样例的受控对照、PyCG 调用图成绩和 SemArc 目录基线。模型业务分组与问答的第三方成绩仍待实测。[首轮源码架构评测](首轮源码架构评测.md)

## 五、逐项阅读笔记与核心公式

下列笔记区分“论文原式或等价改写”“开源实现规则”和“迁移到本项目的建议”。工程框架与定性研究用数据结构、操作或设计原则说明机制。公式只承担其原本能回答的问题。

### 架构与业务语义恢复

**1. ArchAgent — Scalable Legacy Software Architecture Recovery with LLMs（Pan 等，IEEE ICASSP 2026）。** 先提取静态依赖并分块生成摘要，再从入口追踪下游调用或依赖。可用时加入跨仓 API 和文档信号，生成多视图架构。原文 §3 的分块数为 $G=\lceil T/M\rceil$，$T$ 是仓库摘要的总 token 数，$M$ 是单次输入预算。§4.1 请工程师分别核对层、节点、边，并补记漏项。对我们最有用的是让入口和下游共享上下文，并把漏项计入评测。按 token 预算分块时，同一业务流程仍可能被截断。[正式论文][aa-doi] · [全文 §3–4][aa-paper] · [ArchEval][aa-data]

**2. SemArc — Software Architecture Recovery Augmented With Semantics（Zhao 等，IEEE TSE，2026 年 1 月刊）。** 从代码读出实现层职责，用典型架构模式辅助推断架构层职责。作者实现分别接收 `CodeSem` 和 `ArchSem`，结合结构依赖做社区划分。公开实现中的锚点聚类分支遍历同组件的候选文件对，若对应方向已有边，将其权重更新为 $w'_{ij}=2w_{ij}$，随后再运行社区检测。这是该分支的一步。工作台可分别保留“为何同属一组”和“谁调用谁”的依据，用人工文件成员表评测分组。[正式论文][sem-paper] · [实现第 675–731 行][sem-impl] · [作者标注][sem-labels]

**3. ASNER — Software Architecture Recovery with Adaptive Semantic Neighborhoods and Evidence-Grounded Refinement（2026 年 10 月 arXiv 预印本）。** 用文件的主要职责、管理对象、状态影响生成表示，将静态依赖、语义邻居及目录线索用于初分组。随后只对边界不清的文件比较保留、移动或暂缓。原文式 (2) 的关键量为 $K_{\mathrm{gap}}(i)=\arg\max_{1\le k<q_i}(S_i^{(k)}-S_i^{(k+1)})$。$S_i^{(k)}$ 是第 $k$ 高相似度，$q_i$ 是有效候选数。算法再用项目规模上限和最低保留比例裁剪邻域，短序列和并列情况见其附录。工作台可让关系接近的文件成为候选，由职责与源码决定是否归并。新增的语义边留在分组推断层。[全文 §3.2–3.5、附录 C][asner]

**4. Towards Lightweight Domain Model Reverse Engineering from Source Code（Mancas 等，MODELS 2026）。** 会议题名如上，作者公开全文和复现实验使用另一题名 *Towards Automated Domain Model Extraction from Source Code using Heuristics and Open-Source LLMs*。先把类及其关系整理成简化表示，再根据领域文档排列候选，交由可本地运行的模型迭代区分领域概念和实现细节。核心相似度是 $\cos(u,v)=(u\cdot v)/(\lVert u\rVert\lVert v\rVert)$，其中 $u,v$ 表示类名与文档片段的嵌入。可把排序当作阅读顺序，为概念筛选提供代码和已识别概念。Python 项目常由函数、路由和脚本承载业务，需把这些也纳入候选，在 Python 样本上重验。[会议论文页][domain-paper] · [全文 §3–4][domain-full] · [复现实验包][domain-data]

### 调用关系、条件与第三方问答评测

**5. PyCG — Practical Call Graph Generation in Python（Salis 等，ICSE 2021）。** 静态分析迭代求出函数、变量、类和模块标识符之间的赋值关系，再据此解析可能的调用目标，可处理一部分高阶函数和动态语言特性。简化后，每个调用位置沿赋值关系定位函数对象，再产出调用方和被调用方的配对。原论文给出分析规则和微型、应用级评测，报告的调用边代表静态分析结果。工作台可读取作者发布的期望边，定位我们错在目标解析、符号对齐还是收录范围。[正式论文与方法][py-paper] · [2021 固定工件][py-art]

**6. Dependency-Based Extraction of Conditional Statements for Understanding Business Rules（Hatano 等，IEICE，2016）。** 研究 Java 单方法内影响指定 setter 输出值的条件。做法是从目标调用反向缩小控制流图，再用控制依赖、数据依赖寻找影响输出参数的判断。论文 §4 的一个关键集合可等价写为 $V_S=\{v\mid\exists s\in S,\ v\leadsto_{\mathrm{CFG}}s\}$，其中 $S$ 为目标调用对应的指令，路径可长为零。这个集合限定候选范围，下一步用依赖分析选出影响输出的条件。工作台可为“是否执行动作”和“动作写入什么值”分别取证。原文实验针对 Java 方法，要单测迁移后的 Python 异常、提前退出与跨函数路径。[期刊论文][hatano] · [作者全文 §4][hatano-full]

**7. RepoProbe — Benchmarking Architecture-Aware Repository Comprehension with Checklists（Yang 等，ASE 2026）。** 从真实开发者讨论构建开放题，每题有参考答复、1 至 4 个知识项和一个表达项，每个知识项有预先给定的离散分档。按论文 §4 的记法等价改写，$s=\sum_i s_i+c$，知识项最高分合计为 9，$c\in\{0,1\}$。总体分取各题 $s/10$ 的均值，另报知识分、表达分和满分率。清单经专家验证，论文的逐项判分使用模型。可复用原始题和清单。“源码是否支持”是我们增设的维度，单独出分，由人抽样复核。[正式论文][rp-doi] · [全文 §4–5][rp-paper] · [原始题库][rp-data]

**8. SWE-QA — A Dataset and Benchmark for Complex Code Understanding（Laila Elkoussy 与 Julien Perez，LREC 2026）。** 用解析器抽取实体，再辅助生成多跳选择题和干扰项。题型分别侧重“声明—使用”以及“多个实体协作”。**原评测指标**为答对率，可写作 $A=N^{-1}\sum_{i=1}^{N}\mathbf{1}[\hat y_i=y_i]$。答案是选项编号，输入中可含作者整理的上下文。可用它做方法链和证据检索的受控对照，计分时再看实体和片段是否覆盖正确位置。猜中选项本身不足以支持一段业务讲解。[论文][swe-paper] · [数据字段与许可][swe-data]

### 开源设计与产品对照

**9. CodeBoarding（MIT 开源分析引擎和 CLI）。** 静态分析抽取符号和依赖，模型组织组件、生成说明，输出 `analysis.json`，其中有组件、关系和源码引用。界面支持组件展开、依赖导航及跳转到代码。**核心机制**是静态关系、语义说明、交互呈现之间的数据接口，交互质量适合用读者任务衡量。对标时可固定一个 Python 提交，同时比较模块边界、箭头解释和到达源码的步骤。记录所用引擎与界面版本。[源码、输出结构与交互说明][cb]

**10. Arch Lens（MIT 开源）。** 作者定义一份可编辑的分析 JSON，包含系统、组件、关系、边界和要回答的问题。`validate` 验证结构与引用，`check` 对照 Git 和文档重新解析引用，`compare` 比较两版分析。架构图和说明共享同一输入。**核心机制**是“声明—证据—版本”的可追溯关系。工作台可用受影响的声明组织复核，把“源行变化”和“业务含义变化”分开记录。引用存在只能完成前一层检查。[项目、命令和分析示例][lens]

**11. CodeQL 的 Python 控制流设计（GitHub 官方文档）。** 一个 Python 语法节点可对应零个、一个或多个控制流节点，例如 `finally` 可由不同路径进入。基本块能用于可达性与互斥关系查询。**核心关系**可写为 $A\leadsto B$，表示控制流图里从块 $A$ 有路到 $B$。要知道具体输入是否走过这条路径，还需要额外证据。可用返回、抛异常、正常落入后续语句的例子检验条件提取。若已有 Python 分析能通过相同用例，可沿用现有实现。[官方示例与查询][codeql]

**12. Google Code Wiki（产品设计对照）。** 官方公开了高层解释到文件、类和函数的跳转、自动生成的架构/类/时序图，以及以 Wiki 为上下文的 Gemini 问答。**可核查的机制**是上述产品行为。算法细节与准确度在这份产品介绍中未披露。可对照读者能否带着同一个问题在图、问答和代码之间往返，用相同任务测完成效果。[Google 官方介绍][wiki]

### 交叉学科可以移用什么

**13. 自然语言处理 · ALCE — Enabling Large Language Models to Generate Text with Citations（Gao 等，EMNLP 2023）。** 把生成回答的质量拆为内容、表达和引用质量。对回答中第 $i$ 个陈述 $s_i$ 及其引文集合 $C_i$，论文 §3.3 的引用召回率可写为

$$
R_{\mathrm{cite}}=\frac{1}{n}\sum_{i=1}^{n}\mathbf{1}[C_i\ne\varnothing \ \land\ \phi(\mathrm{concat}(C_i),s_i)=1].
$$

$\phi$ 判断引文合起来是否蕴含陈述。精确率逐条考察引文。若整组已支持陈述，但某条不能独立支持且移除后仍获支持，该条计为无关。工作台可据此检查一句话需要的多段代码是否齐全，再另测根本没写出来的条件。原文评估的是自然语言文段，Python 分支取反、提早返回和执行顺序要由代码事实或人工复核。[论文首页][alce] · [全文 §3.3][alce-full]

**14. 数据库 · Provenance Semirings（Green、Karvounarakis、Tannen，ACM PODS 2007）。** 用符号标注输入元组，并在查询运算中保留输出的来源。在正关系代数中，联合对应加法，连接时共同参与的证据对应乘法。例如，$ab+cd$ 保留两种推导，第一种共同使用 $a,b$，第二种共同使用 $c,d$。映射到工作台，同一条业务箭头下的两处调用可以各自成立，各处又有自己的条件证据。界面应展示两条独立来源，避免把两处条件搭配错误。该代数解释证据组合。执行顺序、条件真假与异常仍按 Python 控制流记录。[作者论文，§§2–4][prov]

**15. 人机交互与可视化 · A Nested Model for Visualization Design and Validation（Munzner，IEEE TVCG / InfoVis 2009）。** 把领域任务与数据、抽象操作与数据类型、视觉编码与交互、算法与效率列为四个验证层次。上层任务界定决定下层该测什么。**核心方法是为不同层次分别取证。** 对当前项目，四层分别对应“读者要确认什么业务行为”“哪些对象及路径承载答案”“能否读懂条件并回到调用行”“渲染与检索是否及时”。实验应给读者具体问题并记录答案与耗时，让算法准确率与读图体验各自有证据。[作者论文和验证框架][munzner]
