# 首轮源码架构评测

本轮检验三个读图问题。一个调用在什么条件下发生？两个业务职责为什么被归在同一组？改过源码后，旧总览的哪些引用需要重查？对照工具为 v0.3.0 `aecd78a`。模型相关的归并实验使用冻结的 DeepSeek 讲解和固定提议，两版收到的输入相同。[实验设计](开发流程与创新方向参考.md)

## 一个调用点对应哪些条件

先在固定的 Scrapy 提交上阅读三个文件，记下不同调用各自适用的分支和提前退出，再对照两版工作台。测试给两版的总览事实提取器传入相同的 5 条引用，每条只指向一个调用行，检查它能补出哪些条件。表中的行号来自同一提交。

| 预先选定的位置 | v0.3.0 总览只引用调用行时 | 本轮生成的证据 |
| --- | --- | --- |
| 重定向中两次调用同一方法，L169 和 L172 | L169 有 L168 的真分支，L172 没有列出条件事实 | 两处都能查到 L146–151、L154–155、L165–166 的提前返回和 L157 的断言。L169 走 L168 的真分支。到达 L172 时，此前若走该分支，已在 L169 返回。[重定向源码](https://github.com/scrapy/scrapy/blob/f9a98603066240bcb7065f3058018b8cb068a656/scrapy/downloadermiddlewares/redirect.py#L145-L172) |
| 调度器磁盘入队 L254、内存入队 L259 | L254 没有条件事实，L259 只有 L256 的假分支 | 两个位置都能回到 L251 判断和 L253 的去重返回。只有 L259 的证据里出现 L255 断言和 L256 假分支。断言说明注明 Python 启用优化时会跳过该检查。[调度器源码](https://github.com/scrapy/scrapy/blob/f9a98603066240bcb7065f3058018b8cb068a656/scrapy/core/scheduler.py#L249-L260) |
| 导出设置分支内的 L512 | 将下标判断笼统讲成字典或列表是否为空 | L501 的判断对象是 `self.settings['FEED_URI']` 取出的配置值。还可追到 L497–498 抛出 `NotConfigured` 的分支。[导出设置源码](https://github.com/scrapy/scrapy/blob/f9a98603066240bcb7065f3058018b8cb068a656/scrapy/extensions/feedexport.py#L497-L513) |

这 5 个调用里，在只引用调用行的总览中能打开相关条件事实的，从 **3/5 增至 5/5**。整仓前后均有 6,246 个节点、12,404 条原始关系。按文件组成协作模块时，可分别展开的生产调用或入口绑定从 489 处增至 1,214 处，新增 725 处位于模块内部。这些数据衡量证据的可见范围。5 个调用是人工核对样本，无法代表整个仓库的条件召回率。[条件提取](../how2trust/collaboration.py) · [总览提取](../how2trust/overview_facts.py)

模型审校也使用按调用点整理的证据。在历史订单快照上，用原先的 9 条总览、19 个节点讲解重建单批审校请求，11 个调用位置的短引用都能在同一请求的源码中找到。这个实验验证发送给模型的材料。另用本地测试模型验证，同一方法在同一行出现两次也能按列区分，只含断言或条件实参的小项目也会进入审校。[单批证据构建](../how2trust/semantic_evidence.py) · [请求与缓存回归](../tests/test_batch_call_evidence.py)

## 两个职责为什么会合并

多仓订单里，取消订单和可售退货分别在 L157、L186 调用 `Desk.retry`。对两版工作台给出同一个合并提议，将取消、退货、重试归为“订单重试”，理由仅指向共享的 `retry`。旧版接受该提议，新版保留 3 个职责，并保留两处可打开的调用。另一项回归用两段各自扣减库存的实现，确认模型能凭各组实际执行的代码完成合理归并。[订单实现](../audit/terra-fulfillment/project/dispatchdesk/store.py#L141-L187) · [归并回归](../tests/test_capability_domains.py)

这验证了合并决策如何使用证据。首轮讲解阶段已赋予同一标签的成员仍沿用原有归属。此次没有用新模型重新生成 Scrapy 业务分组，整仓业务讲解质量没有获得第三方分数。

## 源码改动后哪些总览引用需要复核

以下四次实验都使用同一份 9 条结论的订单 DeepSeek 历史图。改动施加在源码副本上。

本轮可打开的订单示例由新版工作台重绘历史快照。历史图与本次重扫有相同的源文件、34 个节点、93 条关系和产品树，分析器的诊断记录有差异，因而两个快照的指纹不同。重绘沿用原快照与原讲解的绑定，并从其中的源码重新计算调用条件。

在这 9 条历史结论中，有 2 条引用了动作，却没有引全该动作已识别的判断或退出行。第 4 条引用了 L185–186 的可售判断与重试，读者还需要补读 L168–170 的退货条件和 L172 的拒绝。第 7 条也讲退货，原有引用已覆盖这些检查。工作台把缺引的具体行列在对应结论下。这个标记只回答“引用覆盖了哪些行”，文字是否已经解释了该行为要结合原句阅读。[订单源码](../audit/terra-fulfillment/project/dispatchdesk/store.py#L160-L187) · [逐行覆盖回归](../tests/test_overview_facts.py)

| 对副本的改动 | 逐条结果 |
| --- | --- |
| 保持原始源码 | 9 条引用仍匹配 |
| 在 `store.py` 文件头插入 3 个空行 | 8 条位置移动，1 条引用仍匹配 |
| 只将 L185 的可售退货判断由 `==` 改为 `!=` | 第 4、7 条标出实现变化，其余 7 条引用仍匹配 |
| 移除 L185–186 的判断和重试调用 | 2 条的原证据缺失，1 条位置移动，6 条引用仍匹配 |

工作台比较旧结论引用的原文、已解析调用目标及已识别的执行条件。引用仍匹配表示这些证据可以对应到当前版本。旧总览没有写到的业务行为、一个复合句的语义是否完整，仍需另行核对。[历史业务图](../audit/fulfillment-deepseek-improved/architecture.html) · [证据比较实现](../how2trust/claim_drift.py)

复现时，第一条命令传入 PyCG 数据仓库的 `data/micro-benchmark` 目录，第二条传入 Scrapy 仓库根目录和 SemArc 的标注文件。为第二条追加 `--graph 业务图.html` 可以评分同一源码快照的模型业务分组。逐例差异和路径对齐清单分别写入 JSON。

```powershell
python tests/bench_pycg.py D:/bench/pycg-evaluation/data/micro-benchmark --json pycg-results.json
python tests/bench_semarc.py D:/bench/scrapy D:/bench/scrapy_gt.json --source-prefix scrapy --json scrapy-results.json
python -m how2trust check-evidence audit/terra-fulfillment/project --previous audit/fulfillment-deepseek-improved/architecture.html --json order-evidence.json
```

本轮通过 144 项 Python 回归测试和 7 套浏览器测试。浏览器覆盖在线上传旧图、点回当前源码、协作模块内部下钻、模型设置、圈选问答和窄屏显示。对同一冻结订单快照分别用两个 Python 哈希种子导出，HTML 字节一致。[工作台浏览器测试](../tests/workbench_views.cjs) · [旧图核对浏览器测试](../tests/compare_evidence.cjs)

RepoProbe 的仓库级问答、真实模型重新生成后的讲解质量，以及读者在图上找到正确证据所需的时间，本轮均未测量。
