# 交付审阅（可选）

架构工作台可以单独使用。需要对比两次交付、查看历史报告或运行已有检查清单时，可使用本页命令。示例命令均在 How2Trust 根目录执行。

## 验收 coding agent 的一次交付

直接打开 `examples/delivery-review.html` 可查看一份已执行检查的报告。示例同时包含通过的要求、失败的要求、尚未验证的要求、吞掉异常的分支、用途待说明的新函数以及明确禁止的导出功能。

**Windows 下双击 `Review.cmd`**，选择交付目录，填写开工前的 Git 提交或选择旧版目录，提供原始任务或验收清单，然后生成 HTML。在防御和范围页可以逐项展开证据、定位差异行、写下自己的判定及理由，并导出复核记录。

命令行可以复现同样的结果。以下 PowerShell 示例从本项目目录启动。将报告写到被比较目录之外，方便反复运行时保持输入不变。

```powershell
# 复现随附的示例，实际运行基线与交付版本的行为检查
.\How2Trust.cmd review examples/delivery/submission --base-dir examples/delivery/baseline --spec examples/delivery/contract.json --run-checks -o examples/delivery-review.html --json examples/delivery-review.json

# 验收自己的 Git 仓库；BASE_COMMIT 为 agent 开工前的提交
.\How2Trust.cmd review D:\projects\my-app --base BASE_COMMIT --spec D:\tasks\acceptance.json --run-checks -o D:\tasks\delivery.html --json D:\tasks\delivery.json

# 在对应版本的架构工作台打开报告，从交付差异跳到类或方法，并就验收资料追问
.\How2Trust.cmd serve D:\projects\my-app --review D:\tasks\delivery.json --open
```

其他平台可将 `.\How2Trust.cmd` 换成 `python -m how2trust`。默认比较基线和当前工作树，覆盖已提交、暂存、未暂存及未忽略的新文件；用 `--head COMMIT` 可锁定某次交付。目录比较模式读取两个目录中除 Git 元数据外的文件。报告保留二进制摘要和删除前的差异，重命名分别显示旧文件删除、新文件增加。符号链接和子模块作为变更项记录，执行检查的临时副本会列出跳过的链接。

### 三个判断分别依据什么

| 问题 | 可核对的依据 |
| --- | --- |
| 要求是否完成 | 每条要求对应行为检查、期望、实际输出和退出码。同一检查分别在基线与交付的临时副本执行。缺少检查或选择静态审阅时显示“未验证”。基线本来就通过的检查也会列出。 |
| 是否过度防御 | 比较新旧 Python 语法树，标记新增的宽泛吞异常、异常回退、异常重试和重复守卫。详情列出所处理的场景、成本、复核问题和源码位置。仅在清单明示禁止某种模式时自动判违规；必要性由实际失败场景和需求裁决。 |
| 是否节外生枝 | 将改动行分配到文件、类或函数，匹配原始要求约定的位置。即使函数本身获准修改，新增的可写文件操作也会单列复核，显示操作和源码行。明示禁止的范围另标为违规。 |

### 提供原始要求与验收依据

`--spec task.md` 或 `--spec task.txt` 可直接开始审阅。工具同时保留原文，将普通段落和列表项按顺序纳入验收清单，列表项的续行保留在该项内。没有检查的要求保持未验证。希望工具实际判定行为时，提供 JSON 清单。最好使用开工前确认的清单和独立检查程序。若清单本身出现在本次改动中，报告会提示核对。

```json
{
  "task": "只允许取消待发货订单，本次不增加导出功能。",
  "requirements": [{
    "id": "R1",
    "text": "拒绝取消已发货订单，保留 shipped 状态",
    "scope": ["orders.py::cancel_order"],
    "checks": [{
      "name": "对已发货订单发起取消",
      "argv": ["{python}", "{spec_dir}/probe.py", "shipped"],
      "expect": {"exit": 0, "stdout": "rejected shipped"},
      "timeout": 15
    }]
  }],
  "forbidden": ["orders.py::export_ledger"]
}
```

- `scope` 和 `forbidden` 接受仓库相对路径和 `路径::限定符号`，如 `app/orders.py::OrderService.cancel`。路径里的 `*` 匹配一个路径段中的字符，`**` 可跨目录。
- 若要求允许写入具体文件，可在该要求中声明 `"writes": ["orders.json"]`。只有范围选择器命中且代码中的目标路径字面量相同，才有这项明确授权。对 `path = Path("telemetry.log")` 后执行的 `path.write_text(...)`，工具也会检查该写入是否需要复核。网络请求、数据库写入和自定义包装函数需另设行为检查。
- `forbiddenDefenses` 可选，仅填写项目已经明确禁止的模式。可选值为 `swallowed-exception`、`fallback`、`retry`、`duplicate-guard`。
- 检查命令以参数数组传给操作系统。`{python}` 是运行 How2Trust 的解释器，`{repo}` 是当前受测版本的临时副本，`{spec_dir}` 是清单所在目录。`expect` 可核对退出码、完整标准输出 `stdout` 或其中的非空片段 `contains`，默认期望退出码为 0。比较器分块读取完整标准输出，包含条件也能命中长日志末尾的标记。整段比较按 UTF-8 读取，统一换行并忽略一个结尾换行。
- 只有显式启用 `--run-checks` 或在向导中勾选运行时才执行清单里的命令。每项检查使用独立的基线和交付副本，使用当前用户权限和本机依赖。命令超时或无法启动时，报告会注明原因。直接运行测试时，如果有用例通过，同时有用例跳过或预期失败，检查显示“部分验证”。只有跳过或预期失败时显示“未验证”。单独约定的业务输出不符时显示“检查失败”。每个输出流最多展示前 128,000 字节。
- 在报告中保存“需要补充证据”后，可以在“需要关注”筛选中继续跟踪该项。点开“部分验证”的要求可以看到通过、跳过和预期失败的用例数。
- `review` 命令成功写出报告时返回 0；需求是否通过由报告中每条要求的 `status` 表示。HTML 包含差异与检查日志。人工判定保存在浏览器，使用“导出复核记录”另存 JSON。配置模型后，带报告的架构工作台支持查询原始要求、检查结果和变更归属。

## 从原始要求起草场景

开工前可从需求起草验收场景。双击 `Review.cmd`，选择模型配置与原始要求，点「从原始要求生成场景草案」。检查前置条件、操作与预期结果后，在编辑框中保存并载入。命令行也支持相同操作。

```powershell
.\How2Trust.cmd draft --spec audit/business-workbench/发货需求.txt --llm-config providers.json -o my-scenarios.json
```

场景草案保留原始需求，`checks` 初始为空。将核定的场景名称用作同一需求下检查的 `name`，并指定自己的独立验收脚本。脚本向标准输出写一个 JSON 对象，例如 `{"first":{"state":"partial"}}`，则 `expect.json` 中的 `"/first/state": "partial"` 会核对实际字段。每一项的预期值、基线实测、交付实测均出现在报告中。只检查命令正常退出的业务场景显示未验证。如果需求本身约定退出码，使用 `verifies: "exit"`。可用 `source` 指定源码符号，加上 `trace: true` 记录该符号在可观测 Python 进程中实际执行的行。[可运行的发货验收清单](../audit/business-workbench/contract.json) · [正确版与错误版的复现脚本](../audit/business-workbench/verify-shipping.py)
