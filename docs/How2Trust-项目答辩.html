03 / 前人工作与项目贡献

已有方法如何服务于持续审阅？

已有研究能恢复调用图和架构组件。我们进一步关注读者怎样核查一条业务解释，以及代码改动后哪些解释需要重新生成。

04 / 核心特点 · 代码分块缓存

改的是调用方，被调用方的讲解也可能过时

coding agent 往往每轮只改一处。再次生成业务图时，工作台先在本地重建静态事实，再判断哪些材料值得重新发给模型。

  1. 把生产源码划成稳定的阅读批次按目录、文件和源码顺序组织，在预算允许时保留完整类或函数。块内带行号的源码有独立内容指纹。
  2. 把调用上下文纳入复用判断请求包含本阶段实际使用的源码、关系或审校材料。即使函数体没变，调用方改变的条件也能使相关请求失效。
  3. 逐阶段复用已验证的回复同一仓库和模型配置下，提示与请求内容相同即可从磁盘复用。初读能沿用而审校材料变化时，只重做相应审校。

05 / 增量重绘实验

小改动后，模型少读了多少？

在含订单、发货、报表的测试仓库中，只把订单入口的 order.ready 改为 order.paid。对同一份改后源码，分别用空缓存和上轮缓存生成整仓业务讲解。

18.46%

少发送 3,848 个输入字符

两次生成的讲解文件内容完全一致。另一次只改测试注释时，生产业务讲解的新增模型请求为 0 次。

较大仓库的对照。 在 Scrapy 固定提交 f9a9860 中反转一个调度条件，93 个初读请求中有 92 个指纹相同。发生变化的请求占 30,405 / 2,579,847 个初读输入字符。

订单实验使用本地固定回复模型，测量实际发送的字符。Scrapy 实验在本地比较请求指纹，仅涵盖初读。两项均未测量云端计费 token 或费用。

07 / 证据与评测

哪些结论经得起核查？

调用关系、条件可见性、旧证据的变化是三个独立的问题。把它们分开测量，才能知道读图时哪一步仍需要人工判断。

81 / 119

预测的调用对中有多少命中？

在 PyCG 的 112 个 Python 微型用例上，工作台预测 119 对调用，命中参考集 254 对中的 81 对。精确率为 68.07%，召回率为 31.89%。

按调用方与被调用方去重。赋值别名会造成漏边，构造函数的表示差异也计入不匹配。

3/5 → 5/5

这里测量的是所选调用的证据可见性，样本规模为 5。
