## 01　从代理生成的源码重建产品架构　0:00–0:17

各位老师好。用编程代理写代码时，即使所有测试都通过了，我仍需要把它做出来的产品和最初的设想逐项对照。How2Trust 帮我从源码里看清代理实际做出的产品。

## 02　测试通过后仍需核对产品架构　0:17–0:48

假设我请代理实现“取消订单”，测试验证了待支付的订单可以取消。我原本还希望拦住已发货订单的取消请求。如果规约和测试都漏掉了这条限制，待支付订单的测试照样会通过。从意图写成规约，再从规约落到代码，这两步都可能丢掉业务条件。我们希望让使用者能看见代码已经作出的决定，再和自己的预期对照。

## 03　从 Python 仓库到可核查的业务图　0:48–1:31

拿到一个 Python 仓库后，我先把目录拖进启动器。工作台读取当前源码，在本地生成结构图，入口、类和方法调用已经可以浏览。接下来配置本地或云端模型，我可以解读全部生产代码，也可以只圈一部分。模型给出业务职责，程序把引用接回源码。看图时，我点开一条箭头就能读到调用与条件，也可以追问、批注，最后导出能离线查看的 HTML。代理再改代码，我就重新载入仓库，对照新图安排下一轮修改。

*指图时，沿图从左上走到右下，在“导出与再更新”处停一下。*

## 05　模型按业务职责归并源码符号　2:08–2:48

有了调用关系，我们还需要把共同完成一项业务的函数放在一起。模型分批读取生产源码和相关调用，为符号提出业务职责，并给出文件和行号。工作台先查找符号定义，再核对引用的行号。有效的引用必须落在该符号或相关调用的源码范围内。模型如果还想合并两个组，就要给出双方成员各自的实现证据。自分析图里的“静态调用条件分析”有十二个成员。展开后，右侧六层调用链的每一步都能点回代码。跨组的调用点则汇总成业务模块之间的箭头。

## 08　源码指纹标识批次，请求指纹决定复用　3:45–4:30

分块缓存来自开发过程中的一个具体需求。代理可能只改一行排序，大部分源码都没变，我却仍要更新整张业务图，把新版本的产品行为和原先的意图对照。系统按路径组批，同目录的小文件可以合并，大文件优先沿类和函数边界拆开。第一种指纹记录这批源码的路径、行区间和原文。第二种指纹记录某个阶段的指令和完整输入。这样既能沿用没变的解读，也能识别函数没改、调用上下文却变了的情形。

*指图时，先指左侧的源码指纹，再指右侧的阶段请求指纹。*

## 09　调用条件变动后，按阶段更新讲解　4:30–5:03

举个例子，place 调用 ship。代理把调用方远处的提前退出条件从 ready 改为 paid，ship 本身一行没改。初读 ship 时，节选没包含那条判断，草稿还能复用。复核会沿控制流把退出条件找回来，这次材料里出现了 paid，所以只需为 ship 重新发一次复核请求。新增和删除的代码先反映在当前静态图里，各阶段再根据各自的输入复用结果或重新请求。

## 13　用外部基准检验 How2Trust 的输出　6:50–7:38
